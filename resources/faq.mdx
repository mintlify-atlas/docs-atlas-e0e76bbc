This FAQ collects the most common questions developers ask when getting started with EDA Agent or migrating existing applications to an event-driven architecture. If you don't find your answer here, open a discussion on the [GitHub repository](https://github.com/hodophile/eda-agent).

<AccordionGroup>

  <Accordion title="What Node.js version does EDA Agent require?">
    EDA Agent requires **Node.js 16 or later**. The framework relies on native `async/await` and `Promise`-based APIs throughout its core — no polyfills or transpilation of async primitives is needed. Using a current LTS release (18 or 20) is strongly recommended for production deployments.
  </Accordion>

  <Accordion title="Can I use EDA Agent with TypeScript?">
    Yes. EDA Agent ships with full TypeScript type declarations out of the box, and TypeScript is the recommended way to use the framework. Because event payloads flow through the system as plain objects, TypeScript generics let you define strongly-typed event contracts at the point of both publication and subscription:

    ```typescript
    import { Agent } from 'eda-agent';

    interface OrderPlaced {
      orderId: string;
      total: number;
    }

    agent.subscribe<OrderPlaced>("order.placed", async (event) => {
      // event.payload is typed as OrderPlaced
      console.log(event.payload.orderId);
    });
    ```

    Type-safe contracts catch mismatches between publishers and subscribers at compile time rather than at runtime, which is especially valuable in large codebases with many event types.
  </Accordion>

  <Accordion title="How do I share state between event handlers?">
    The recommended approach is to **avoid shared mutable state entirely**. Design your events so that each event carries all the information its handlers need — this is the core principle of message-passing in event-driven systems.

    If coordination between handlers is genuinely necessary, use an **external store** such as Redis, a relational database, or another persistent backend, and access it from within each handler independently:

    ```typescript
    agent.subscribe("user.verified", async (event) => {
      // Read and write through an external store, never a shared in-process variable
      await db.users.update({ id: event.payload.userId }, { verified: true });
    });
    ```

    Sharing mutable in-process variables across handlers leads to race conditions when `concurrency` is greater than 1 and makes handlers difficult to test in isolation.
  </Accordion>

  <Accordion title="Are events delivered in order?">
    Events are **enqueued in the order they are published** to the bus. However, because handlers execute concurrently (up to the configured `concurrency` limit), a later event may complete processing before an earlier one — particularly when handlers involve I/O of different durations.

    If strict ordering is required:

    - Set `concurrency: 1` in your `AgentOptions`. This serialises all handler invocations so that each event is fully processed before the next begins.
    - Alternatively, manage ordering logic inside your handlers (e.g., by storing a sequence number in an external store and processing out-of-order events after their predecessors have been confirmed).

    ```typescript
    const agent = new Agent({ name: "ordered-agent", concurrency: 1 });
    ```

    <Warning>
      Setting `concurrency: 1` eliminates the throughput benefits of parallel handler execution. Use it only when ordering guarantees are strictly required by your domain.
    </Warning>
  </Accordion>

  <Accordion title="What happens if a handler throws an error?">
    EDA Agent catches all errors thrown inside handlers so that a single failing handler cannot crash the entire agent or block subsequent events. The error lifecycle works as follows:

    1. The handler throws (or returns a rejected `Promise`).
    2. If `retries` is configured, EDA Agent re-invokes the handler up to that many times.
    3. If every retry is exhausted (or `retries` is not set), the `onError` callback is invoked with the error and the original event.
    4. The agent continues running and processes subsequent events normally.

    ```typescript
    const agent = new Agent({
      name: "resilient-agent",
      retries: 3,
      onError: (err, event) => {
        console.error(`Handler failed for event ${event.type}:`, err);
        // Send to alerting system, dead-letter queue, etc.
      },
    });
    ```

    <Tip>
      Use the `onError` callback to forward failed events to a dead-letter queue or emit an alerting metric so failures are visible in production observability tooling.
    </Tip>
  </Accordion>

  <Accordion title="Can I run multiple agents in the same process?">
    Yes. You can instantiate as many `Agent` objects as you like within a single Node.js process. Each instance maintains its **own independent event bus** and its own subscriber registry, so events published to one agent are not visible to another:

    ```typescript
    import { Agent } from 'eda-agent';

    const billingAgent = new Agent({ name: "billing-agent" });
    const notificationAgent = new Agent({ name: "notification-agent" });

    await billingAgent.start();
    await notificationAgent.start();
    ```

    Each agent manages its own lifecycle independently. You can start, stop, and publish events to each agent without affecting the other.
  </Accordion>

  <Accordion title="How do I test event handlers?">
    EDA Agent is designed with testability in mind. There are two complementary strategies:

    **Unit testing** — Because handlers are plain async functions that accept an event object, you can import and invoke them directly without starting an agent:

    ```typescript
    import { handleOrderPlaced } from "./handlers/order";

    it("sends a confirmation email", async () => {
      const event = { type: "order.placed", payload: { orderId: "123", email: "user@example.com" } };
      await handleOrderPlaced(event);
      expect(mailerMock.send).toHaveBeenCalledWith("user@example.com");
    });
    ```

    **Integration testing** — Create a real `Agent` instance with a short `timeout`, publish events programmatically, and assert on observable side effects:

    ```typescript
    import { Agent } from 'eda-agent';

    it("processes payment on order.placed", async () => {
      const agent = new Agent({ name: "test-agent", timeout: 500 });
      agent.subscribe("order.placed", handleOrderPlaced);
      await agent.start();

      await agent.publish({ type: "order.placed", payload: { orderId: "abc", total: 49.99 } });
      await new Promise((r) => setTimeout(r, 100)); // allow handler to run

      expect(paymentServiceMock.charge).toHaveBeenCalled();
      await agent.stop();
    });
    ```
  </Accordion>

  <Accordion title="What's the difference between agent.publish() and agent.bus.publish()?">
    These two methods both deliver an event to the bus, but they operate at different levels of abstraction:

    | Method | Recommended | Validates agent state | Enriches metadata |
    |---|---|---|---|
    | `agent.publish()` | ✅ Yes | ✅ Yes | ✅ Yes |
    | `agent.bus.publish()` | ⚠️ Advanced only | ❌ No | ❌ No |

    `agent.publish()` accepts a `PublishInput` object (`{ type, payload, metadata? }`) and is the **recommended public API**. Before forwarding to the bus, it verifies that the agent has been started, then automatically enriches the event envelope with a generated `id`, the current `timestamp`, and the agent's `source` name.

    `agent.bus.publish()` accepts a full `Event` object and is a lower-level escape hatch that bypasses all agent-level checks and metadata enrichment. It exists for advanced scenarios such as bridging an external message broker into the bus, where you want to preserve original metadata from upstream systems.

    <Warning>
      Calling `agent.bus.publish()` on a stopped or uninitialised agent can result in events being lost or handlers never being invoked. Prefer `agent.publish()` in application code.
    </Warning>
  </Accordion>

  <Accordion title="Does EDA Agent support persistence or event replay?">
    By default, EDA Agent uses an **in-memory event bus with no persistence**. Events that are published when no handler is subscribed are discarded immediately and cannot be replayed. The in-memory design keeps the framework lightweight and dependency-free for the common case.

    For persistence and replay, integrate EDA Agent with an external message broker and bridge incoming messages into the agent:

    ```typescript
    // Bridge Redis Streams into EDA Agent
    redisStreamConsumer.on("message", async (streamMessage) => {
      await agent.publish({ type: streamMessage.type, payload: streamMessage.payload });
    });
    ```

    Popular broker choices include:

    - **Apache Kafka** — high-throughput, long-term log retention, native replay
    - **RabbitMQ** — flexible routing, dead-letter queues, acknowledgements
    - **Redis Streams** — low-latency, consumer groups, built-in persistence

    <Info>
      When bridging a broker, use `agent.bus.publish()` if you want to preserve the original event `id` and `timestamp` from the broker rather than generating new metadata.
    </Info>
  </Accordion>

  <Accordion title="How do I stop an agent gracefully in production?">
    Register OS signal handlers that call `await agent.stop()` before the process exits. The `stop()` method drains all in-flight events and waits for active handler invocations to complete before resolving — preventing data loss or partially-processed events during deployments or restarts:

    ```typescript
    import { Agent } from 'eda-agent';

    const agent = new Agent({ name: "production-agent" });
    await agent.start();

    const shutdown = async (signal: string) => {
      console.log(`Received ${signal}. Shutting down…`);
      await agent.stop();
      process.exit(0);
    };

    process.on("SIGTERM", () => shutdown("SIGTERM"));
    process.on("SIGINT", () => shutdown("SIGINT"));
    ```

    <Tip>
      Container orchestrators such as Kubernetes send `SIGTERM` before forcibly killing a process after a grace period. Ensure your `agent.stop()` drain time is shorter than the orchestrator's `terminationGracePeriodSeconds` to avoid hard kills.
    </Tip>
  </Accordion>
